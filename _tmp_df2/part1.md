## 1. Вывод синтезатора

**Что действительно никто не отгружает.** Если отфильтровать 67 предложений по порогу «novelty ≥ 4 и impact ≥ 4», остаётся 26, и они складываются не в список фич, а в четыре связных тезиса. Первый — **резюмирование без компилятора** (#18 загрузчик + `on:click="module#export"`, #19 `resume()` по аннотациям, #20 checkpoint именованных сигналов, #21 `ctx.step()` как continuation token): Qwik-подобные три артефакта (состояние, подписки, ссылки на код) записываются в HTML руками или печатаются dev-эмиттером, и остров поднимается по лестнице L0→L5 без переписывания. Второй — **HTML как версионируемый поток, а не одноразовый ответ** (#24 morph против фронтира стримингового парсера, #25 Merkle-morph с `Aegis-Have`/`data-aegis-keep`, #26 `fragment()` как SWR-запись, #27 навигация с отложенным коммитом): ни один HTML-over-the-wire движок не морфит по мере прихода чанков и не принимает receiver-side signatures на уровне фрагментов. Третий — **движок, который знает время и причину** (#7 EDF-планировщик с полосами-дедлайнами, #46 `pace()` с гистерезисом, #52 INP, разложенный на фазы flush и привязанный к острову, #51 трассирующий хребет с причинным родителем «сигнал → effect → fetch → Server-Timing → commit»): pull-based эффекты Aegis допускают частичный flush без двойного состояния, а это ровно то, чего React добивается VDOM-переносом, а Solid отказывается делать вовсе. Четвёртый — **local-first как спецификация, а не продукт** (#36 `query()` с IVM, #37 лог намерений с rebase, #39 Sync Protocol v1, #40 shapes): Replicache/Zero/Electric — отдельные 30–100 KB библиотеки, Aegis может вместить это в ~6–8 KB поверх существующего entry/patch-log/persist/leader. Отдельно стоят #57 (диагностика как протокол с machine-applicable правками — компилятор Rust умеет, ни один рантайм-фреймворк нет), #23 (гибернация островов и строк по `contentvisibilityautostatechange` — память пропорциональна видимому, а не данным), #6 (`transaction()` — OCC поверх уже существующих `version()`/`_depsChanged`), #42 (DeltaBlue-планировщик для форм) и #47 (кинематическое предсказание цели указателя за 150–300 мс до hover).

**Что честно назвать догоняющим.** Значительная часть раунда — это исправление того, что платформа уже умеет, а движок эмулирует хуже: #17 `moveBefore()`, #28 `parseHTMLUnsafe`/DSD, #29 Trusted Types (сегодня `html\`\`` падает под `require-trusted-types-for`), #31 CloseWatcher/popover и починка `command()` (раздел с Invoker Commands сегодня не работает — `--` не нормализуется), #32 URLPattern, #33 CompressionStream. Это S-задачи с impact 3–4 и нулевым функциональным риском (fallback = сегодняшний код), их надо сделать первыми именно потому, что они дешёвые и закрывают реальные дыры. Туда же — #63 запись в js-framework-benchmark, #65 политика стабильности (сначала починить упаковку: `aegis.js` в git — ядро без `island`, первый пример README не запускается), #66 fitness-CI с интерлив-храповиком, #61 единый источник документации. Ни одно из них не ноу-хау, но без них ноу-хау никто не увидит: три разных числа размера ядра в README и ни одного git-тега — это то, по чему senior-инженер закрывает вкладку. Несколько предложений с высокой новизной, но спорной отдачей (#13 inline-кэш со сворачиванием констант в мастер-шаблон — красиво, но экономия единицы микросекунд; #21 durable setup; #34 LEDBAT; #16 cost-based планировщик DOM) стоит делать после того, как измерители (#22, #10, #66) покажут, что именно там узкое место. Один вопрос линзы S закрыт отрицательно с числами: кросс-сессионный кэш компиляции и `new Function`-tier не окупаются (≤ 29 µs на шаблон, < 10 ms на страницу из 300 шаблонов) — фиксируем как осознанное решение (#15).

**Во что превращается тезис движка.** Сегодня Aegis — «zero-build, server-first, маленький, с большим набором батареек». Если построить бриллианты, тезис становится точнее и агрессивнее: **«единственный движок, который резюмирует серверный HTML без компилятора, морфит его по мере стриминга, планирует эффекты по дедлайнам, объясняет каждое взаимодействие и каждый запрос причиной, и даёт local-first по открытой спецификации — всё под строгим CSP и в бюджете 4–60 KB, выбираемом tree-shaking».** Три линзы независимо пришли к одному и тому же структурному паттерну — «Versioned reads, logged writes» (X), «Delta collections» (S+X), «Intent log» (L): движок уже хранит версию каждого источника и умеет складывать base + patches, но использует это только внутри синхронного flush. Поднять версии и логи из flush наружу — в async-работу (#6), в коллекции (#14), в персист (#38), в сеть (#34, #39), в планы DOM (#16) — это не набор фич, а один сдвиг архитектуры, который отличает Aegis от всех signal-фреймворков в списке сравнения. Второй сквозной паттерн — «Runtime-as-Oracle» (A) и «Nullable sink» (O): тот же рантайм, который ловит ошибки LLM 69 детекторами, должен выдавать их как машинные правки, грейдить сгенерированный код в CI и отдавать OTel-спаны в проде — цена при выключенном состоянии равна одной проверке на null. Если резюмировать в одну фразу: Aegis перестаёт быть «маленьким Solid для Django» и становится **рантаймом с семантикой базы данных для HTML-страниц** — версии, логи, запросы, транзакции, планы, объяснения.

## 2. Новые паттерны и практики

Каждый паттерн — в форме «проблема → силы → решение → следствия → известные применения», с пометкой: **[НОВЫЙ]** — сочетание, которого нет ни в одном UI-движке; **[ПЕРЕНОС]** — известная практика из другой области, впервые перенесённая; **[ПЕРЕИМЕНОВАНИЕ]** — известная практика под новым именем.

### 2.1. Resume Ladder — Лестница резюмирования (R) — [НОВЫЙ]
- **Проблема.** Zero-build движок не может сериализовать замыкания, поэтому Qwik-резюмируемость «в лоб» недостижима; бинарный выбор «гидрация или компилятор» оставляет server-first страницы платить за перерисовку того, что сервер уже сделал.
- **Силы.** CSP (никакого eval); бюджет размера (ядро 4.3 KB); острова очень разной формы (счётчик ↔ редактор); Twig/Blade-разметка, которую пишут не JS-разработчики; требование «тот же код работает и в клиентском рендере».
- **Решение.** Представить резюмирование как три артефакта-данных в HTML — состояние (`<script data-aegis-state>`/journal), подписки (`data-aegis-text/attr/…`) и ссылки на код (`on:click="module#export"`) — и лестницу уровней, измеримую одним счётчиком: L0 перерисовка (сегодня, wasted ≈ 100 %), L1 adopt/claim (0 мутаций, setup выполняется), L2 checkpoint (собственное состояние переживает reload/remount), L3 journal (асинхронный пролог воспроизводится синхронно), L4 resume (setup не выполняется, только handler-ы), L5 loader (движок не нужен до первого события).
- **Следствия.** Два словаря обработчиков и привязок (шаблон vs серверный HTML) и контракт стабильности имён — сглаживаются dev-эмиттером `annotate()` и E-кодами; выигрыш растёт с числом островов и падает для одного тяжёлого клиентского приложения.
- **Известные применения.** Qwik (компилятор печатает те же три артефакта), Stimulus `data-action` (грамматика module#method), Temporal/Durable Functions (журнал шагов как continuation), Android savedInstanceState / CRIU, event sourcing (снимок + журнал), проекции Футамуры (аннотированный HTML как специализация программы по серверному входу).
- Предложения: #18, #19, #20, #21, #22.

### 2.2. Speculative Specialization with Per-Use Guards — Спекулятивная специализация с локальным guard'ом (S) — [ПЕРЕНОС]
- **Проблема.** Часть фактов о шаблоне известна статически (strings), часть — только во время выполнения (вид значений, форма массива, набор ключей объекта), а в zero-build/CSP-мире нет ни компилятора, ни eval.
- **Силы.** На одном call-site динамические факты почти всегда мономорфны; корректность не может зависеть от кэша; деопт не должен быть глобальным — уже отрендеренные экземпляры трогать нельзя; бюджет байтов ограничен.
- **Решение.** Для каждой единицы работы (часть шаблона, список, вызов мутатора) хранить наблюдаемую форму и специализированный аппликатор; перед каждым использованием — дешёвый guard (shape-тег, `Object.is`, seq лога); промах → generic-путь только для этого использования, megamorphic после k промахов, откат спекулятивных изменений общего состояния (unfold мастера, сброс лога).
- **Следствия.** Быстрый путь для ~95 % сайтов при неизменной семантике; конечный автомат из трёх состояний на единицу; нужна model-based проверка переходов; память O(единиц).
- **Известные применения.** Inline caches Smalltalk/Self и V8 (hidden classes, field constness), self-rewriting AST в Truffle, plan caching с parameter sniffing в SQL Server/Oracle, 2-битные насыщающие счётчики предсказателей переходов, adaptive radix/learned indexes с fallback на B-tree, incremental view maintenance.
- Предложения: #12, #13, #14, #16.

### 2.3. Receiver-side Signatures for HTML-over-the-wire — Вектор версий фрагментов (W) — [ПЕРЕНОС]
- **Проблема.** Передача и дифф страницы стоят O(page), а изменение — O(fragment); наивная замена уничтожает клиентское состояние DOM (острова, фокус, скролл, медиа).
- **Силы.** Сервер уже версионирует фрагменты (cache keys / template digests), но выбрасывает это на границе ответа; клиент владеет состоянием, которого сервер не видит; стриминг требует in-order, close-on-arrival семантики; HTTP-кэши не должны отдавать дельту одного клиента другому.
- **Решение.** Клиент шлёт версии, которые держит (`Aegis-Have: id=v;…`), сервер отвечает пустыми заглушками `data-aegis-keep` для неизменных фрагментов, morph пропускает любое поддерево с совпавшим `data-aegis-v` — Merkle-сравнение сверху вниз, где хэши даёт получатель.
- **Следствия.** Передача и дифф пропорциональны изменению; состояние DOM сохраняется по построению; стриминг-совместимо (заглушки закрываются мгновенно); нужны `Vary: Aegis-Have`/private caching, версия как истинная функция содержимого (record + template digest + locale/role), уникальность id; неверная версия = молча устаревший UI → dev-warn на kept id, отсутствующий в DOM.
- **Известные применения.** rsync (получатель шлёт сигнатуры блоков), Merkle-анти-энтропия Dynamo/Cassandra/Riak, RFC 3229 delta encoding (A-IM/IM), Git thin packs, ESI per-fragment TTL, ETag/If-None-Match на уровне объекта.
- Предложения: #25, #26, #24.

### 2.4. Deadline-class Lanes with Owner-atomic Preemption — Полосы как дедлайны, вытеснение на границе владельца (P) — [НОВЫЙ]
- **Проблема.** Реактивный движок должен одновременно не разрывать согласованность UI внутри компонента, отвечать на ввод < 50 мс и не давать фоновой работе голодать.
- **Силы.** Синхронный flush прост и glitch-free, но монолитен; приоритетные уровни (React lanes) требуют старения и ручных правил против голодания; time-slicing в VDOM требует двух версий состояния; pull-based эффекты читают актуальное значение в любой момент запуска — частичный flush безопасен на уровне эффекта, но не на уровне «половина компонента обновилась».
- **Решение.** Одна очередь эффектов, упорядоченная абсолютным дедлайном `t_cause + D[class]` (input 50, frame 16, transition 250, idle 2000 мс), где класс определяется причиной записи (событие, `startTransition`, кадр), а не объявлением эффекта; исполнитель проверяет бюджет среза и `isInputPending` только на границе группы эффектов одного корневого scope; продолжение через `scheduler.yield()`/MessageChannel.
- **Следствия.** Старение бесплатно (истёкший дедлайн сам всплывает первым); голодание ограничено ровно одной группой; худшая добавка к latency ввода = max стоимость группы + один yield; tearing возможен лишь между компонентами и лишь на один кадр; семантика «DOM обновлён сразу после записи» держится только в синхронной части и через `flushSync()`; нужен инжектируемый планировщик для тестов.
- **Известные применения.** EDF (Liu & Layland 1973), Linux SCHED_DEADLINE, Tokio cooperative budget и Erlang reductions, Volcano/pipelined execution, Blink task priorities + `scheduler.yield()`, React 18 transitions/selective hydration как ближайший фронтенд-аналог (но с VDOM-переносом состояния вместо pull-чтения).
- Предложения: #7, #8, #9, #11.

### 2.5. Dual-liveness Leak Audit — Двойная живучесть (M) — [ПЕРЕНОС]
- **Проблема.** В системе с явным владением (scope/effect-дерево) и GC утечка невидима для обоих по отдельности: GC не собирает узел, потому что он законно висит в `subs` живого сигнала; фреймворк не считает его утечкой, потому что счётчики растут «законно».
- **Силы.** GC недетерминирован (FinalizationRegistry-канарейки flaky); счётчики не называют виновника; строгий реестр всех узлов в проде — цена памяти; корни владения размыты (компоненты, `root()`, orphan `createScope`, синглтоны i18n/theme).
- **Решение.** `leak := GC-live ∧ ¬owner-reachable`, где owner-reachable — детерминированный обход дерева владения от явного множества корней; GC-live — dev-реестр наблюдателей либо точный подсчёт по прототипу через CDP `Runtime.queryObjects` после принудительного GC. Разность — список с site/owner/holds.
- **Следствия.** Утечки становятся assert'ом (фаззер I11, heap-гейт в CI); появляются обязательные законы — единственное ребро владения, транзакционный dispose, явные корни, аффинный перенос.
- **Известные применения.** Linux kmemleak, Valgrind memcheck («still reachable» vs «definitely lost»), Android LeakCanary, Chromium queryObjects/Oilpan-тесты, Rust (владелец = статический root set), Effective Java Item 7.
- Предложения: #1, #2, #3, #4, #5.

### 2.6. Query-as-sync-unit + Intent Log — Предикат как единица синхронизации, лог намерений как единица записи (L) — [ПЕРЕИМЕНОВАНИЕ: Replicache/Zero/ElectricSQL, впервые внутри UI-движка]
- **Проблема.** Клиентский кэш с ключом-URL не может быть локальной БД: строка живёт в N копиях, свежесть принадлежит ответу, конфликт разрешается на уровне «весь ответ», оптимистичные правки — замыкания, которые нельзя переиграть, сервер не может сказать «что изменилось с X».
- **Силы.** Мгновенные локальные чтения/записи и честный offline; данных больше, чем влезает; разнородный бэкенд должен получить реализуемую спецификацию; бандл zero-build должен остаться маленьким; корректность (сходимость, read-your-writes, отсутствие рваных чтений) проверяема симуляцией.
- **Решение.** Нормализованный граф сущностей с версией строки и индексом держателей; живые запросы с IVM (дельта строки → O(log n) в индексе запроса); запись только через именованные чистые мутаторы → намерения с монотонным id, переигрываемые поверх каждого серверного снимка и отбрасываемые по `lastMutationID`; транспорт с курсором сервера (cookie), вектором версий клиентской группы и poke; единица репликации — shape (коллекция + where с журналом move-in/move-out и offset).
- **Следствия.** URL превращается в seed/транспорт, `resource()` — в запрос над графом; «стадо» на reconnect заменяется одним дельта-pull; мигание optimistic исчезает структурно; цена — эталонный сервер и спецификация как часть продукта, чистота мутаторов, ограниченный язык where.
- **Известные применения.** Логическая репликация Postgres (слот + LSN, tombstones), Bayou/Coda, Calvin, Materialize/differential dataflow, git rebase, Replicache/Zero/ElectricSQL/Linear.
- Предложения: #35, #36, #37, #39, #40.

### 2.7. Multi-way Constraint with Edit-recency Scheduler — HotDrink/DeltaBlue для форм (F) — [ПЕРЕНОС]
- **Проблема.** В UI одни значения выводятся из других в обе стороны (net↔gross, единицы, «любые два из трёх», сумма-100), а реактивные графы строго односторонние: два эффекта, пишущих друг друга, — бесконечный цикл; авторы латают это `activeElement`-проверками и флагами-замками.
- **Силы.** Пользователь вправе перебить любую вычисленную величину; система всегда согласована; нельзя перезаписывать только что введённое; нужно знать, какое поле сейчас «вычислено»; решение живёт над существующим односторонним графом.
- **Решение.** Каждой переменной — edit-stamp; каждому ограничению — метод на направление (in → out); планировщик выбирает метод с выходом в переменную с самой давней правкой (walkabout strength), никогда — в только что правленную; ацикличность проверяется, исполнение топологическое в одном `batch()`.
- **Следствия.** Переопределение пользователем бесплатно; «вычисленность» — побочный продукт выбора метода; методы чистые и идемпотентные; линейные неравенства требуют Cassowary (отдельный модуль).
- **Известные применения.** DeltaBlue/SkyBlue (ThingLab, Garnet, Amulet), HotDrink property models, Cassowary в Apple AutoLayout/Kiwi, spreadsheet-семантика, bidirectional lenses (Foster et al.).
- Предложения: #42, #41, #44, #45.

### 2.8. Latency Ladder with Hysteresis — Лестница воспринимаемой задержки (H) — [ПЕРЕИМЕНОВАНИЕ: Nielsen-полосы + Schmitt-триггер, впервые как дефолт движка]
- **Проблема.** У async-операции один boolean `pending`, а пользователю нужна разная обратная связь на разных отметках времени; фидбэк короче перцептивного JND хуже, чем никакого.
- **Силы.** Быстрые пути (кэш, 304, prefetch) делают большинство ожиданий < 200 мс; медленные хвосты существуют; пользователи скринридеров не могут пропустить озвученный шум; логика (double-submit guard, abort) должна реагировать при t=0, визуал — нет; команде нужна одна политика.
- **Решение.** Из boolean вывести стадийный сигнал — wait (< 100–150 мс: ничего), busy (индикатор, затем hold ≥ 300–400 мс), slow (≥ 1 с: прогресс/ETA + polite-анонс), stuck (≥ 10 с: abort/retry) — и привязать визуал/анонсы/эскалацию к стадии, а не к boolean.
- **Следствия.** Ноль мерцания на быстрых путях, честная эскалация на хвостах, детерминированные тесты под fakeClock, одна настраиваемая политика; цена — до `hold` мс намеренной задержки после быстрых-но-не-мгновенных завершений.
- **Известные применения.** Schmitt trigger, курсоры ожидания ОС (macOS ~2 с), React Suspense 300 ms fallback throttle и `spin-delay`, hedged requests (Dean & Barroso), staged alarms в авиации/медицине.
- Предложения: #46, #50, #48, #49.

### 2.9. Nullable Sink / Late-bound Tracer — Диагностический канал для tree-shaken движка (O) — [ПЕРЕИМЕНОВАНИЕ: diagnostics_channel / static keys]
- **Проблема.** Движок без сборки должен давать production-телеметрию, но лёгкие секции не могут ссылаться на тяжёлую секцию по имени, а стоимость при выключенной телеметрии должна быть неотличима от нуля.
- **Силы.** Горячие пути (`_flush`, `Signal.set`, `on()`) исполняются миллионы раз; esbuild режет только недостижимый код; экспортёр нуждается в структурных данных, не строках.
- **Решение.** Один модульный `let _tel = null` в §0 и хуки `_tel && _tel(kind, ref)` с малыми целыми kind и передачей уже живых объектов без аллокаций; тяжёлая секция устанавливает сток через `_reg` (@__PURE__) и обязана не удерживать ссылки дольше фиксированного окна.
- **Следствия.** Стоимость при выключенном — одна загрузка + ветвление; включение в рантайме на проде без пересборки; хуки — стабильный внутренний контракт, тестируемый фейковым стоком; риск — соблазн добавлять хуки в `Signal.set`.
- **Известные применения.** Node.js diagnostics_channel, Linux tracepoints + static keys, DTrace USDT, Go `trace.enabled`, Java JFR `isEnabled()`, OpenTelemetry API-vs-SDK.
- Предложения: #51, #52, #53, #54, #55, #56.

### 2.10. Runtime-as-Oracle — Рантайм как оракул (A) — [НОВЫЙ]
- **Проблема.** Код, сгенерированный LLM для zero-build фреймворка, синтаксически корректен, но семантически сломан (потерянная реактивность, утечки вне scope, async в effect), и без компилятора нет статического линтера.
- **Силы.** Zero-build запрещает шаг сборки; ошибки видны только при исполнении; LLM ремонтирует тем лучше, чем точнее фидбэк (позиция + правка); документацию для LLM нельзя проверить без измерений.
- **Решение.** Сам рантайм — источник структурированной истины: детекторы выдают диагностики в машинном формате с applicability-правками; тот же рантайм в strict-режиме — грейдер conformance-eval; тот же рантайм отдаёт контракт страницы (`describe`/manifest) и инструменты (WebMCP).
- **Следствия.** Детекторы обязаны быть точными (ложное срабатывание в strict = сломанный eval) — dev-режим становится частью продукта; провалы eval без предупреждения — бэклог новых детекторов; llms.txt упорядочивается по измеренной частоте ошибок; дев-тексты и схемы должны сворачиваться в прод.
- **Известные применения.** rustc `MachineApplicable` + `cargo fix`, PostgreSQL `HINT:`/`EXPLAIN (FORMAT JSON)`, property-based testing и test-oracle problem, Elm/Rust-ошибки, Apple App Intents/WebMCP.
- Предложения: #57, #58, #59, #60, #61, #62.

### 2.11. Two-phase Navigation & Platform-primitive-over-emulation — Двухфазная навигация (B) — [ПЕРЕИМЕНОВАНИЕ: 2PC / admission webhooks]
- **Проблема.** SPA-движок эмулирует то, что браузер делает для cross-document переходов и DOM-состояния (редиректы до смены URL, стек close-requests, top layer, перемещение узла без потери состояния, парсинг DSD), и эмуляция всегда теряет часть семантики.
- **Силы.** Поддержка старых браузеров; движок должен оставаться маленьким; поведение в двух ветках обязано совпадать для уже написанных тестов.
- **Решение.** (1) Выделить точку, где семантика «прощупывается» одной функцией (`_move`, `_parseHTML`, `onNavigate` с флагом `pre`, `_zip`); (2) feature-detect по наличию API; (3) fallback = ровно сегодняшний код; (4) для навигации — prepare (guards, redirect, loader; может менять цель и отменять без следа) и commit (history-запись, рендер).
- **Следствия.** Движок уменьшается там, где платформа зрелая; тесты гоняются дважды (с API и с `globalThis.X = undefined`); поведенческие различия между ветками документируются.
- **Известные применения.** 2PC и Kubernetes admission webhooks (mutating = redirect, validating = guard); HOT-updates PostgreSQL / `rename(2)`; Lit/React 19.2/idiomorph 0.7 для moveBefore; Hono/Deno для URLPattern; Chrome DevTools/YouTube для CloseWatcher.
- Предложения: #27, #17, #28, #31, #32, #33.

### 2.12. Interleaved Statistical Ratchet — Интерлив-храповик (E) — [ПЕРЕИМЕНОВАНИЕ: Perfherder/compare.R + size-limit]
- **Проблема.** Количественные качества (байты, ms, память, INP) деградируют по 1 % за коммит, а ворота-ступеньки на шумных CI-машинах либо молчат, либо лгут.
- **Силы.** Шум раннера ±20 % против регрессий в 5 %; желание фиксировать улучшения; невозможность держать эталонную машину; сравнивать с эталоном (vanilla, baseline-коммит), а не с абсолютом.
- **Решение.** Мерить пару «эталон vs кандидат» в одной сессии с чередованием ABAB; решение — Манн–Уитни с двумя порогами (p < 0.01 и ratio > 5 %); для монотонных метрик baseline — храповик; один машиночитаемый отчёт, из которого генерируются все внешние цифры.
- **Следствия.** Ложные тревоги ≤ 1–2 % при n = 15, регрессии 5 % ловятся за один коммит, улучшения не откатываются незаметно; цена — удвоенное время бенчмарка и сборка baseline-коммита (git worktree).
- **Известные применения.** Node.js compare.R, Mozilla Perfherder, Chromium Pinpoint, BenchmarkTools.jl `judge`, js-framework-benchmark, quality ratchet (Ford/Parsons/Kua), size-limit/bundlesize.
- Предложения: #66, #63, #67, #65.

### 2.13. Versioned Reads, Logged Writes — Версионированные чтения, журналируемые записи (X) — [НОВЫЙ синтез]
- **Проблема.** Реактивный движок, который знает только «что-то изменилось», не может рассуждать об async-работе, персисте, коллекциях, планах DOM или собственном трафике — только пере-выполнять или пере-диффить всё.
- **Силы.** Zero-build single ES module с жёсткими бюджетами; per-source версии уже существуют (`version()`, `_depsChanged`); замыкания удобны как единица изменения, но непрозрачны; лёгкие секции не должны ссылаться на тяжёлые.
- **Решение.** Каждое чтение записывает увиденную версию, каждая запись — что она сделала, как данные: read set для валидации (OCC), op-лог для fold и персиста (WAL), delta-лог вместо диффа (DBSP), plan-лог с фактическими стоимостями (LEO), delay-сэмпл для следующего бюджета (LEDBAT). Логи — ограниченные кольца с одним правилом: разрыв или reset = «полный пересчёт».
- **Следствия.** Валидация и fold стоят O(затронутых записей), не O(состояния); ops должны быть сериализуемы — замыкания становятся второсортными (warn, только память); два пути (инкрементальный и полный) доказываются эквивалентными оракульным фаззом; каждая подсистема получает `explain()`/`stats()` бесплатно.
- **Известные применения.** OCC/STM (Kung & Robinson; Harris et al.), ARIES (Mohan), Kafka log-as-truth (Kreps), DBSP/differential dataflow, LEO (IBM DB2), LEDBAT/BBR, CLOCK/working-set (Corbató, Denning).
- Предложения: #6, #14, #38, #16, #34, #23.
